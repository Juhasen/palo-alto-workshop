Anatomy

A skill is a folder of Markdown

Only the description is always in context. The rest loads when the skill runs.

.claude/skills/

    SKILL.md

    SKILL.md

    mocking.md
  ticket-to-pr/

Frontmatter

name, description (when to trigger), optional model and disable-model-invocation.

Body

Goal, process, stop conditions. State goals, not keystrokes.

Reference files

Detail the body links to, loaded only when needed: tests.md, templates, checklists.

Gotchas

The most valuable lines. Each one is a failure you saw and never want again.

Everything here is plain Markdown, which is why it fits Palo Alto's rules: no runtime, no installer. Point out reference files: tdd keeps its long guidance in tests.md and mocking.md so the main file stays short.

Invocation

Two ways a skill starts

Model-invoked

Claude picks it when the task matches

description: Diagnosis loop for hard bugs.
  Use when the user says "debug this",
  or reports something failing.

Examples: tdd, code-review, diagnosing-bugs, pr. The description is a trigger, so write it as conditions.

User-invoked

Runs only when you type it

disable-model-invocation: true

/mattpocock-skills:to-spec

Examples: to-spec, implement, grill-me. Use it for steps with side effects or a human gate. They do not show in Claude's skill list, so type the name.

This explains the most common "the install is broken" moment: after installing Matt's plugin, only the model-invoked skills are listed. The pipeline skills are there; type /mattpocock-skills: and the completion shows them. Our ticket-to-pr skill will be user-invoked too.

Palo Alto rules

Non-negotiable for every skill today

Public skills come in. External calls do not.

No unapproved installs

Caveman, Ponytail, and the Matt Pocock plugin. Nothing else.

No network from the agent

No curl, wget, gh, npx, or URL fetches inside a skill.

Plain Markdown only

No scripts, hooks, or runtimes in skills you adopt.

Services via approved routes

Jira through the connector, other services through the policy broker TBD, or paste.

Same constraints as Part 1, plus the policy broker rule from the other team. The next three slides are how to make a public skill obey them. Also mention the endpoint policies now in force: no reading .env, secrets, credentials, ~/.ssh, ~/.aws or ./build; curl, wget and WebFetch blocked; managed hooks only; no permission changes. The skills we build already follow them.

Adapting a skill · 2 of 3

Every hit gets one of three fixes

Route

Through an approved route

Ticket reads go through the Jira connector. Other services go through the policy broker: TBD: how Claude reaches it

"fetch the ticket" → Jira connector
Replace

With a local file or a paste

The spec becomes .scratch/<id>/spec.md. No connector? Ask the user to paste the ticket.

"publish" → write a local file
Delete

When nothing approved can do it

Drop the curl loop and the bash template. Keep the idea: a failing test is the feedback loop.

curl / .sh → removed
docs/agents/issue-tracker.md  →  Tickets come from Jira via the Claude connector. If it is unavailable, ask the user to paste the ticket and save it to .scratch/<ticket-id>/ticket.md. Specs and sub-tickets are local Markdown under .scratch/. Never call gh, glab, or a web API.
The one config file fixes most of Matt's set at once, because every tracker-aware skill reads it. That is the advantage of composable skills: one adaptation point.

New name

pa-to-spec, not to-spec, so you always know which version ran.

SOURCE.md

Upstream repository, commit, license, and a list of what you changed.

Keep the license

MIT asks only that the notice travels with the copy.

Review upstream

The plugin auto-updates. Diff new versions before you port changes in.

Inside a pa- skill, calls to other skills should point at the pa- versions too, or the chain silently falls back to the unadapted originals. That is a gotcha worth writing down.

3 · Fact-check

A fresh reader verifies

Each claim: verified, wrong, or unsupported, with the proving line. Wrong ones are fixed, unsupported ones removed.

This answers the team's request for documentation skills. The fact-check is the point: a confident doc that is wrong is worse than none. In the sample, the check removes "offsets are 64-bit" and the corrected sentence exposes the Windows bug from option A.
